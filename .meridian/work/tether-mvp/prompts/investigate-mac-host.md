# Investigate: what it takes for tether to run on a Mac host

Jimmy expects tether to run on his Mac too (AGENTS.md: POSIX, Linux and macOS). Today it can't (probe p125: `.meridian/work/tether-mvp/serve-mac-probe.md`; `src/auth/.context/TODO`): (1) the daemon looks for tailscaled's LocalAPI only at `/var/run/tailscale/tailscaled.sock` / `/var/run/tailscaled.socket`, which the macOS Tailscale app (here 1.104.2, `/Applications/Tailscale.app`, group container `group.W5364U7YZB.io.tailscale.shared`) doesn't provide, so every request is `503 identity_unavailable`; (2) `tailscale serve --bg unix:<path under /tmp>` was accepted but every request 502'd.
Establish on this Mac, with evidence, no repo edits:
- **LocalAPI:** how the macOS `tailscale` CLI reaches the app's LocalAPI (Tailscale's `safesocket` package: the same-user-proof port + token, via `lsof` on the IPNExtension process or a `sameuserproof-<port>-<token>` file; read upstream source at the matching version). Prove it with a throwaway client that calls `/localapi/v0/whois?addr=…`, `/status`, `/serve-config` and gets real answers. Note the trust properties (who can read the token; does the port check the caller's uid).
- **Serve target:** which Unix-socket paths the app's sandboxed extension can connect to (try `$XDG_RUNTIME_DIR`-like dirs under the user's home, the app's group container if writable, `/tmp`, `/var/folders/...`), and whether it forwards the same identity headers as on Linux. If no Unix socket works, what loopback TCP Serve gives and how tether could make it safe (auth.md explains why a TCP forward was rejected — read its reasoning and say whether a mitigation, e.g. requiring the LocalAPI-verified peer for every request rather than trusting headers, restores it).
- Read `docs/design/auth.md` (Serve publication, node admission, the probe gates) and `src/auth/` to say exactly what code would change.
