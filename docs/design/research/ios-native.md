# iOS native shell: external facts

Web research, sources checked 2026-10-21 (meridian spawn p6). Confidence is given per
claim; items marked inference are not from a source.

## 1. WebAuthn/passkeys and private hosts

- **AASA and entitlement are required.** Apple says a `WKWebView` uses WebKit’s Web Authentication handling, but the service’s RP ID must be configured as the app’s associated domain. Without a `webcredentials` association, the request errors; the app can’t use passkeys for RP domains it hasn’t associated. Apple’s sample requires both the entitlement and an AASA file containing the app’s App ID under `webcredentials`. ([Supporting passkeys](https://developer.apple.com/documentation/authenticationservices/supporting-passkeys), Apple documentation, current page checked 2026-10-21; [Connecting to a service with passkeys](https://developer.apple.com/documentation/authenticationservices/connecting-to-a-service-with-passkeys), Apple sample, current page checked 2026-10-21.) **Confidence: high.**
- **Default AASA retrieval conflicts with a tailnet-only hostname.** Since iOS 14, Apple’s associated-domains system requests AASA through an Apple-managed CDN rather than directly from the server. Apple explicitly documents an alternate mode for servers unreachable from the public internet. Consequently, with normal CDN mode, a tailnet-only `*.ts.net` service that Apple’s CDN cannot reach is likely to fail association setup. **Inference:** the key issue is Apple’s CDN reaching the AASA origin, not whether the iPhone can resolve/reach the host through its VPN. ([Associated Domains entitlement](https://developer.apple.com/documentation/BundleResources/Entitlements/com.apple.developer.associated-domains), Apple documentation, current page checked 2026-10-21; [Supporting associated domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains), Apple documentation, current page checked 2026-10-21.) **Confidence: high on CDN and alternate-mode behavior; medium-high on the practical failure for this specific hostname.**
- **Developer mode is not a safe assumption for TestFlight.** The entitlement documentation describes the `?mode=developer` alternate mode as allowing only devices in Developer Mode to access that domain; Apple’s debugging note recommends it when running from Xcode, when the server is private, or when CDN caching is inconvenient. **Inference:** this is a development workflow, not a documented TestFlight workaround. Treat TestFlight compatibility as unconfirmed and test it; do not design production passkey enrollment around it. ([Associated Domains entitlement](https://developer.apple.com/documentation/BundleResources/Entitlements/com.apple.developer.associated-domains); [TN3155: Debugging universal links](https://developer.apple.com/documentation/technotes/tn3155-debugging-universal-links), Apple, current pages checked 2026-10-21.) **Confidence: high on documented developer-mode intent; medium on TestFlight exclusion absent an explicit statement.**
- **Native AuthenticationServices is not an apparent bypass.** Apple’s native passkey API takes an RP identifier, but Apple also requires associated domains for passkeys. The browser-specific `ASAuthorization` APIs described for alternative browser engines respond to Web Authentication requests; they don’t establish that an app can register an arbitrary private RP without domain association. ([Supporting passkeys](https://developer.apple.com/documentation/authenticationservices/supporting-passkeys); [Passkey use in web browsers](https://developer.apple.com/documentation/authenticationservices/passkey-use-in-web-browsers), Apple documentation, current pages checked 2026-10-21.) **Inference:** ASAuthorization is not a documented escape hatch from the private-AASA problem. **Confidence: medium-high.**

## 2. Alternative native authentication

A viable alternative is a device-bound P-256 signing key protected by Secure Enclave and Keychain access control. Create the key on-device, register its public key with tether’s daemon, then sign a fresh server challenge after authorization. Keep challenge freshness, nonce binding, and server-side replay rejection in the protocol design.

- Apple documents Secure Enclave private keys as **NIST P-256 only**, generated within the enclave, usable for signing/verification or ECDH; pre-existing private keys cannot be imported into it. ([Protecting keys with the Secure Enclave](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave), Apple, current page checked 2026-10-21.) **Confidence: high.**
- For biometric gating, Apple’s `biometryCurrentSet` access-control flag invalidates the item if the user changes enrolled fingerprints or re-enrolls Face ID. Include `privateKeyUsage` when creating a signing key; Apple documents that without it, signing can fail. `LAContext` supports evaluating access controls and requires `NSFaceIDUsageDescription` in the app’s Info.plist. ([`biometryCurrentSet`](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags/biometrycurrentset); [Secure Enclave](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave); [`LAContext`](https://developer.apple.com/documentation/localauthentication/lacontext), Apple documentation, current pages checked 2026-10-21.) **Confidence: high.**
- **Implementation distinction:** `.biometryCurrentSet` gates a keychain item/key operation; do not assume a separate `evaluatePolicy(.deviceOwnerAuthenticationWithBiometrics)` call itself protects the key. Use access control on the signing key and evaluate the key operation with a suitable `LAContext`. Whether the prompt appears per signing operation depends on the exact access-control flags and context. ([CryptoKit P-256 private-key initializer](https://developer.apple.com/documentation/cryptokit/secureenclave/p256/signing/privatekey/init%28compactrepresentable%3Aaccesscontrol%3Aauthenticationcontext%3A%29), Apple, current page checked 2026-10-21.) **Confidence: high on primitives; implementation must be tested on device.**

## 3. Keyboard control and terminal input

- **A native first responder can own keyboard input independently of the web view.** UIKit documents `inputAccessoryView` for a first-responder text field/text view and allows a custom `inputView`; a custom `UITextView`/`UIKeyInput` responder alongside a `WKWebView` is a plausible pattern for retaining native keyboard ownership while forwarding input to the web UI. ([`inputAccessoryView`](https://developer.apple.com/documentation/uikit/uitextfield/inputaccessoryview); [`UIResponder.inputAccessoryView`](https://developer.apple.com/documentation/uikit/uiresponder/inputaccessoryview), Apple documentation, current pages checked 2026-10-21.) **Inference:** Apple documents the responder mechanics, not this exact two-view terminal arrangement. The app should test focus, keyboard dismissal, rotation, and scroll behavior on device. **Confidence: medium-high.**
- **System bars:** `UITextInputAssistantItem` controls the shortcuts bar on iPad; Apple says its contents are ignored on iPhone. It is not a general documented API to remove every keyboard accessory. A custom responder’s own accessory view is controllable, but removing private WKWebView/form accessories via private API is not a supported strategy. ([`UITextInputAssistantItem`](https://developer.apple.com/documentation/uikit/uitextinputassistantitem), Apple documentation, current page checked 2026-10-21.) **Confidence: high on the documented iPad/iPhone distinction; medium on WKWebView-specific accessory behavior.**
- **Keyboard persistence:** first-responder ownership should help keep the software keyboard up while the web view is tapped or scrolled, but I found no Apple guarantee for this composite layout. **Inference:** tapping web content may not dismiss the keyboard if the native responder remains first responder; gestures or explicit responder changes could still dismiss it. Verify empirically.
- **Hardware keyboard:** UIKit supports `UIKeyCommand` for modifier combinations, and `pressesBegan(_:with:)` receives physical key presses. Use `UIKeyCommand` for recognized shortcuts; test Esc and terminal-style Ctrl combinations because system-reserved commands and responder-chain routing may take precedence. ([`UIKeyCommand`](https://developer.apple.com/documentation/uikit/uikeycommand); [`pressesBegan(_:with:)`](https://developer.apple.com/documentation/uikit/uiresponder/pressesbegan%28_%3Awith%3A%29), Apple documentation, current pages checked 2026-10-21.) **Confidence: high on APIs; medium on complete terminal-key coverage.**
- **Open terminal implementation evidence is limited.** Blink Shell has a public source repository, useful as a codebase to inspect, but I did not verify a specific keyboard architecture from the repository pages fetched. ([Blink Shell source repository](https://github.com/kkpan11/blink-shell), checked 2026-10-21.) I found no sufficiently strong source-backed claim about a-Shell, iSH, or Termius’ keyboard implementation. **Confidence: low for implementation comparisons.**

## 4. Native↔web bridge performance

- `WKScriptMessageHandler` and `WKScriptMessageHandlerWithReply` are supported ways for JavaScript to send messages to native code; the reply-capable API has an explicit reply callback. `evaluateJavaScript` is a native-to-web mechanism. ([`WKScriptMessageHandlerWithReply`](https://developer.apple.com/documentation/webkit/wkscriptmessagehandlerwithreply), Apple documentation, current page checked 2026-10-21.)
- **There is no Apple-published latency guarantee or current benchmark** in the documentation found. A 2015 engineering measurement reported significant `evaluateJavaScript` overhead at the time, then an update noted a WebKit fix that reused JS contexts—too old to use as a current latency estimate. ([WKWebView Communication Latency](https://blog.persistent.info/2015/01/wkwebview-communication-latency.html), 2015.) **Confidence: high that no contractual latency is documented; low for using old measured values today.**
- **Recommendation (inference):** benchmark on the target iPhone; keep per-keystroke transport batched/coalesced or move the terminal transport to native if latency/jitter matters. Avoid a request/reply round trip for every character unless measurements show it is acceptable. Keep message payloads small and avoid synchronous JS evaluation. **Confidence: medium as engineering guidance, not an Apple requirement.**

## 5. Loading, TLS, persistence, and WebSockets

- **Remote HTTPS vs bundled UI:** remote HTTPS is the direct fit for daemon-served UI and avoids custom scheme routing; a bundled UI served through `WKURLSchemeHandler` can support offline startup but introduces asset/versioning and custom-scheme considerations. I found no source that settles this tradeoff for tether; it is an architectural choice. **Inference; confidence: medium.**
- **Tailscale TLS:** Tailscale documents that Serve provides HTTPS using an automatically provisioned certificate; Tailscale’s HTTPS certificate docs say these are Let’s Encrypt certificates, and the public certificate/transparency ledger contains the hostname while access remains tailnet-restricted. So `*.ts.net` TLS is publicly trusted, but the service can remain private through Serve and tailnet ACLs. ([Tailscale Serve](https://tailscale.com/docs/reference/tailscale-cli/serve); [Enabling HTTPS](https://tailscale.com/docs/how-to/set-up-https-certificates), current validation dates shown as 2025-12-10 and page checked 2026-10-21.) **Confidence: high.**
- **Cookies:** `URLSessionWebSocketTask` explicitly supports cookies through its session configuration’s `httpCookieStorage`; WKWebView uses `WKWebsiteDataStore` for website data, with persistent vs nonpersistent store selection. These are separate networking stacks: don’t assume WKWebView cookies automatically authenticate a native `URLSessionWebSocketTask`; explicitly share/copy the needed credential or use a suitable cookie store. ([`URLSessionWebSocketTask`](https://developer.apple.com/documentation/foundation/urlsessionwebsockettask); [`WKWebsiteDataStore`](https://developer.apple.com/documentation/webkit/wkwebsitedatastore), Apple documentation, current pages checked 2026-10-21.) **Confidence: high on documented stores; medium on app-specific synchronization details.**
- **iOS 26 WebSocket report:** WebKit bug 308073, reported **2026-02-17**, describes Safari on iOS 26.3 leaving new WebSockets permanently CONNECTING after background resume. The report itself says a Brave iOS 26.3 WKWebView test reconnected successfully. The reported reproduction is Safari/standalone mode with `ws://` to a LAN server—not a conclusive WKWebView or `wss://` result. ([WebKit bug 308073](https://bugs.webkit.org/show_bug.cgi?id=308073), reporter-submitted, status NEW when fetched.) **Confidence: low-to-medium for tether risk; insufficient evidence to say it affects WKWebView.** Test suspend/resume on the target OS and retain a reconnect/reload recovery path.
- **Native transport option:** `URLSessionWebSocketTask` supports `ws:`/`wss:`, async send/receive, redirects/authentication, and cookies. It is a credible native transport alternative if WebKit socket behavior proves unreliable, but it does not by itself keep the app active in the background. ([`URLSessionWebSocketTask`](https://developer.apple.com/documentation/foundation/urlsessionwebsockettask), Apple documentation, current page checked 2026-10-21.) **Confidence: high on API; medium on suitability pending prototype.**

## 6. Haptics and Share extension

- **Haptics:** `UIImpactFeedbackGenerator` can trigger impact feedback; Apple recommends preparing before the anticipated event. Apple explicitly says calling `prepare()` and immediately triggering feedback does not improve latency; the Taptic Engine needs preparation time. ([`UIImpactFeedbackGenerator`](https://developer.apple.com/documentation/uikit/uiimpactfeedbackgenerator); [`prepare()`](https://developer.apple.com/documentation/uikit/uifeedbackgenerator/prepare%28%29), Apple documentation, current pages checked 2026-10-21.) A web event can request haptics through the native bridge, but Apple provides no bridge-to-haptic latency guarantee. **Inference:** reserve haptics for discrete semantic events, prepare ahead where possible, and measure. **Confidence: high on generator behavior; low on end-to-end latency.**
- **Share extension:** Apple’s Share extension model receives shared content through `NSExtensionContext` and extension items. App and extension can share a group container for files/data; Apple’s technical note discusses safe shared-container access. A practical flow is to copy the incoming photo/file into the App Group container, then have the main app consume it when launched/foregrounded. ([App Extension Programming Guide: Share](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Share.html); [TN2408: Accessing Shared Data from an App Extension and its Containing App](https://developer.apple.com/library/archive/technotes/tn2408/_index.html), Apple, current pages checked 2026-10-21.) **Confidence: high on extension and shared-container model; medium on exact launch handoff UX.**

## 7. TestFlight and cost

- Apple says a TestFlight build is available for **up to 90 days**. Internal testing supports up to 100 App Store Connect users; Apple’s overview says external builds may require review and the first build submitted to an external group is reviewed. Internal testing without external beta review is consistent with Apple’s internal tester documentation, but account roles/build eligibility still apply. ([TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/); [Add internal testers](https://developer.apple.com/help/app-store-connect/test-a-beta-version/add-internal-testers/), Apple, current pages checked 2026-10-21.) **Confidence: high.**
- Apple currently lists Apple Developer Program membership at **US$99/year** (or local equivalent). The free account supports installing to one’s own devices via Xcode, but TestFlight is listed among paid membership benefits. ([Apple Developer Program](https://developer.apple.com/programs), current page checked 2026-10-21.) **Confidence: high.**

## Key design implications for tether

1. **Do not assume passkeys work with a private tailnet-only RP in TestFlight.** AASA CDN behavior is the obstacle; developer-mode bypass is documented for development, not as a production/TestFlight solution.
2. **A Secure Enclave P-256 signing key is the more straightforward native-auth candidate** for a single-user, private service, subject to implementing challenge/replay protections and biometric re-enrollment recovery.
3. **Prototype the native first-responder keyboard arrangement and hardware-key mapping** on the actual iPhone before committing the web terminal’s input architecture.
4. **Test WebSocket recovery on iOS 26/WKWebView with `wss://` and Tailscale Serve after app backgrounding.** The cited bug is not conclusive evidence against WKWebView; native `URLSessionWebSocketTask` is a fallback worth testing.
5. **Measure bridge and haptic latency.** Apple documents the APIs, not real-time performance guarantees.
